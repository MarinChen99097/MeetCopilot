# 模型調度守則（Model Dispatch）

> 讀者：擔任「指揮官」的主對話模型（預設 Sonnet 等級）。
> 本檔所有型號與參數皆於 2026-07-04 在此環境查證（來源：Agent/Workflow 工具 schema＋claude-api skill 快取 2026-06-24）。
> 重新查證方法：看 Agent 工具 schema 的 model 枚舉值；產品程式碼要用的 API model ID 一律先載入 `claude-api` skill，不憑記憶填。

## 原則零：指揮官不下場

主對話（指揮官）只做三件事：**拆解任務、交辦、根據回報做決策**。
大量讀取、掃 repo、查網頁、批次改檔、驗證——一律派 subagent。主對話 context 裡只進結論。
高階思考預算只花在「換便宜模型就掉品質」的判斷：架構取捨、規格衝突、要不要問使用者。

## 一、可用的調度手段（此 harness 查證值）

| 手段 | 怎麼指定 | 查證值 |
|---|---|---|
| Agent 工具（單一 subagent） | `model` 參數 | `"haiku"`、`"sonnet"`、`"opus"`、`"fable"`（fable 額度稀缺且未來未必可用，**不要依賴**） |
| Agent 工具的 effort | — | **沒有 effort 參數**，不要填 |
| Workflow 工具的 `agent()` | `opts.model`＋`opts.effort` | effort：`"low"`｜`"medium"`｜`"high"`｜`"xhigh"`｜`"max"`；省略 model 則繼承主對話模型（**通常太貴，交辦廉價工作時要顯式指定**） |
| subagent 類型 | Agent 的 `subagent_type` | 搜尋用 `Explore`（唯讀）、規劃用 `Plan`、其餘用 `general-purpose` |

Claude API 定價參考（產品程式碼與成本估算用；session 調度只需知道相對貴賤）：
`claude-fable-5` $10/$50、`claude-opus-4-8` $5/$25、`claude-sonnet-5` $3/$15（2026-08-31 前優惠 $2/$10）、`claude-haiku-4-5` $1/$5（context 200K，其餘 1M）。單位：每百萬 input/output token。

## 二、任務交辦三要素（每次交辦缺一不可）

1. **目標與動機**：要達成什麼＋為什麼（subagent 知道意圖才不會答非所問）。
2. **驗收條件**：可檢查的完成定義（「找到 X 並給行號」「測試全綠」「清單含 A/B/C 三欄」）。
3. **回報格式**：明確規定輸出形狀與長度上限（見回報合約）。

填空模板見 `TASK_TEMPLATES.md`——交辦前照抄模板，不要即興。

## 三、調度對照表（sonnet 列已於本專案實測校準，見 L11）

| 任務型態 | 派給 | 理由 |
|---|---|---|
| 搜尋/定位程式碼、掃目錄結構 | `Explore`，`model: "haiku"` | 唯讀、量大、低判斷 |
| 讀多檔後摘要、整理文件 | `general-purpose`，`model: "haiku"`（結果差再升 sonnet） | 機械性 |
| 明確規格的實作、批次套用已知模式 | `general-purpose`，`model: "sonnet"`＋`effort: "high"` | **已實測**：sonnet/high 勝任全端實作 |
| 重構（有測試保護） | `general-purpose`，`model: "sonnet"`＋`effort: "high"` | 同上，已實測 |
| 網路研究、供應商比較 | `general-purpose`，`model: "sonnet"` | 需篩選與交叉比對 |
| 程式碼審查、對抗驗證 | `model: "sonnet"`＋`effort: "high"`；高風險判斷加派第二個獨立 agent | 已實測：找到 15 個真 bug；見「驗證不自驗」 |
| 架構設計、規格衝突裁決、難題除錯、**設計/品味取捨** | 指揮官自己做；仍卡住 → `model: "opus"` 並附完整脈絡 | 「換便宜就掉品質」的部分；設計取捨連 opus 都補不了時攤給使用者（R6/L10） |
| read-back / 存在性驗證 | `model: "haiku"` | 最便宜的 fresh context |

Workflow 的 `agent()` 交辦時：機械階段（搜尋、摘要、read-back）`effort: "low"`；多答案評分 `effort: "medium"`；**實作、重構、程式碼審查/對抗驗證**用 `effort: "high"`（本專案實測 high 勝任，且與上表「程式碼審查用 high」一致）；只有最難的裁決才用 `"xhigh"` 以上。

**平行派多個實作 agent 的守則（L5/L6，慘痛教訓）**：要橫跨「前端↔後端」或任何模組邊界平行派工時：
1. **先凍結共用契約**（路徑、請求/回應欄位形狀、錯誤碼，不只型別）成共用檔或契約清單；每個 agent prompt 明文「一律 import／對照契約，不得自創路徑/欄位，缺什麼回報 gaps」。
2. 整合後**必做真實 client→server 整合冒煙**（用真正呼叫方的請求形狀），不能只各測一邊——否則各 agent 對「各自假設的契約」實作而漂移，曾一次產生 6 個 critical 契約不一致且冒煙全綠沒抓到。

## 四、回報合約（寫進每個交辦 prompt 的最後）

subagent 必須遵守，指揮官交辦時必須明文要求：

- 只回報：**結論＋證據位置（`檔案:行號`）＋（若有）風險或不確定處**。
- 長產物（報告、大段程式碼、清單 >30 行）→ **存檔到指定路徑，回傳路徑**，不要貼內容。
- 禁止貼整檔內容、禁止流水帳過程敘述。
- 失敗時回報：嘗試了什麼、卡在哪、錯誤訊息原文——這是升級時的「失敗軌跡」。

## 五、升降級路徑（照走，不要即興）

```
haiku 出錯 1 次
   → 同任務升 sonnet 重派（附 haiku 的失敗回報）
sonnet 同一子任務連錯 2 次
   → 升 opus 重派，且必須附上「完整失敗軌跡」：
     原始交辦 prompt＋兩次的輸出＋錯誤訊息＋你的驗收條件
opus 也解不了
   → 停，整理問題與軌跡，問使用者
解出「模式」之後（例如 opus 找到了修法）
   → 把模式寫成明確規則，降回 sonnet/haiku 批次套用到其餘同類case
```

**硬限制：同一模型上、同一件事最多重試兩輪**（一輪＝一次交辦＋一次修正）。**換模型升級開新的計數，不消耗前一個模型的輪數**——本限制擋的是「同一模型換個措辭反覆重試」，不是擋升級鏈。
記帳範例：haiku 失敗 1 次（依上方規則升級，合法）→ sonnet 兩輪內連錯 2 次（升級，合法）→ opus 一輪失敗（停，問使用者）——全程不違反硬限制。
任一模型兩輪用盡且不符升級條件、或 opus 也失敗＝方向可能錯了，回 `JUDGMENT_RUBRICS.md` **R4（方向錯誤的訊號）**檢查，而不是再試第三次。

## 六、驗證不自驗

做的人不能自己宣稱做完。驗證一律派 **fresh-context** agent（不共享做事者的上下文，避免確認偏誤）：

| 產物類型 | 驗證方式 |
|---|---|
| 文件/檔案 | read-back：派 haiku agent 讀回檔案，核對「應包含的章節/關鍵內容」清單 |
| 程式碼 | 跑測試或實跑（能跑就跑，不能跑至少讓 agent 讀 diff 找明顯錯誤） |
| 高風險判斷（架構、資安、會影響 I1/I2/I3 的） | 第二意見：另派一個 agent 以「試著反駁這個結論」為任務；或多答案評審擇優 |

驗證 agent 的交辦必須附「驗收條件清單」，讓它逐條打勾/打叉，不接受「看起來沒問題」。
