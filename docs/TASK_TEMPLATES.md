# 任務交辦 Prompt 範本

> 用法：交辦 subagent 前，複製對應範本，把 `【】` 填滿。**不要即興寫交辦 prompt**。
> 每個範本已含三要素（目標與動機／驗收條件／回報格式）與建議模型。
> 模型欄位是 Agent 工具的 `model` 參數；用 Workflow 時另加 effort（見 MODEL_DISPATCH.md 第三節）。
>
> **平行派多個實作 agent 前必讀（實戰教訓 L5/L6）**：若要平行派工橫跨「前端↔後端」或任何模組邊界，
> **先凍結共用契約**（不只型別，連 API 路徑、請求/回應欄位形狀、錯誤碼，寫進共用檔或一份契約清單），
> 每個 agent 的 prompt 都要求「一律 import／對照該契約，不得自創路徑或欄位，缺什麼回報 gaps」。
> 否則各 agent 會對「各自假設的契約」實作而漂移，整合時大量對不上（曾發生 6 個 critical 契約不一致）。
> 整合後**必做真實 client→server 整合冒煙**（見 T2 驗收），不能只各測一邊。

## T1. 搜尋／定位（`Explore`，`model: "haiku"`）

```
目標：找出【要找的東西，例：applyPatch 的 guard 邏輯】的位置。
動機：【為什麼要找，例:我接下來要在它旁邊加 REORDER 的邊界檢查】。
範圍：【目錄或檔案類型，例：src/ 下的 .ts 檔】。
搜尋提示：可能的關鍵字【keyword1, keyword2】；也檢查【別名/舊名】。

驗收條件：
- 給出每個相關位置的 檔案:行號
- 每個位置附 ≤3 行說明它是什麼
- 若找不到，列出你搜過的 pattern 與目錄，不要猜

回報格式：條列，總長 ≤30 行。不要貼大段程式碼。
```

## T2. 實作（`general-purpose`，`model: "sonnet"`）

```
目標：實作【功能，例：deck model 的 INSERT_AFTER 操作】。
動機：【它在系統中的角色，例：這是改造引擎三操作之一，M3 里程碑】。
規格依據：先讀 docs/PRODUCT_SPEC.md 的【章節】。相關既有程式碼在【檔案:行號】。

硬性約束：
- 不可違反 I1/I2/I3（見 docs/PRODUCT_SPEC.md 不變量表）
- 版本保護：本專案是 git repo，階段性 commit 即可回滾（非 git 目錄才用 檔名.bak）
- 只做本任務範圍內的事，不要順手重構別的

驗收條件：
- 【可驗證條件1，例：index <= committedIndex 的 INSERT 被 reject 並回傳原因】
- 【可驗證條件2，例：新增測試 X 與 Y 通過】
- 所有既有測試仍通過（若有測試）
- 若橫跨模組邊界（前端↔後端等）：一律 import／對照共用契約，不得自創路徑/欄位；缺什麼回報 gaps（L5）
- 若可端到端跑：附一支「模擬真正呼叫方的請求形狀」的整合冒煙，不能只測自己這一邊（L6）

回報格式：改動檔案清單（檔案:行號範圍）＋每檔一句話說明＋測試輸出結果。
新增程式碼不要貼回，我會用 read-back 驗證。
若遇到規格模糊處：停在該處，回報問題與你建議的 2 個選項，不要自行擴大解釋。
```

## T3. 重構（`general-purpose`，`model: "sonnet"`）

```
目標：重構【對象】，使【可度量的目的，例：deck 狀態變更全部收斂到單一入口】。
動機：【現在的痛，例：三處各自改 pending 陣列，I1 難以集中強制】。

硬性約束：
- 行為不可變：重構前後對外行為完全一致
- 【若有測試】先跑一次測試記錄基線，重構後必須同樣全綠
- 【若無測試】先為要動的核心路徑補最小測試，再動手
- 每完成一個檔案就存檔，不要攢一批一起存
- 若重構範圍涉及 I1/I2/I3 相關程式碼（見 docs/PRODUCT_SPEC.md 不變量表）：重構後須額外驗證該不變量仍成立（例如用攻擊測試打 guard），不能只靠既有測試綠燈判定

驗收條件：
- 測試基線與重構後結果一致（附兩次輸出）
- 【結構性驗收，例：grep 全 repo 只剩一處直接寫 deck.pending】

回報格式：改動清單＋測試前後輸出＋（若有）行為風險點。
發現「不重構就修不了」的 bug：不要修，記下位置回報。
```

## T4. 研究（`general-purpose`，`model: "sonnet"`）

```
目標：研究【問題，例：串流 STT 供應商比較——Whisper-streaming vs Deepgram vs Google STT】。
動機：【要支撐什麼決策，例：M1 要選 ASR，延遲預算 interim <500ms】。

必答問題：
1.【問題1，例：各家 streaming interim 延遲的官方數字與實測報告】
2.【問題2，例：diarization 是否內建】
3.【問題3，例：每分鐘音訊定價】

要求：
- 每個事實附來源（URL 或文件名）；官方文件優先於部落格
- 分清「官方宣稱」與「第三方實測」
- 查不到的就寫「查不到」，不准編造數字

驗收條件：必答問題全數有答案或明確標「查不到」；附一個你的建議與理由。

回報格式：把完整報告存到【docs/research/主題.md】（Write 工具會自動建立不存在的父目錄），主對話只回：
每個必答問題一行結論＋建議＋報告路徑。
```

## T5. 審查（`general-purpose`，`model: "sonnet"`；高風險加派第二個獨立 agent）

```
目標：審查【對象，例：src/deck/ 的本次 diff】找出真實缺陷。
動機：【背景，例：這段程式碼強制 I1，出錯會讓已播頁被改掉】。

審查重點（依序）：
1. 正確性 bug（邏輯錯、邊界、race condition）
2. 是否違反或可繞過 I1/I2/I3——**授權/隔離不變量要想像用「不該有權的身分」（另一 user／另一 org／非 presenter）去打會怎樣**，不是只看 happy-path（L7）
3. 跨模組契約是否一致（前端呼叫的路徑/欄位 vs 後端實際實作）（L5）
4. 【本次特別關注，例：WebSocket 斷線重連時的狀態一致性】

要求：
- 回報所有發現，包括你不確定的——由我過濾，不要自我審查掉低嚴重度項
- 每個 finding：檔案:行號＋一句話缺陷描述＋具體失敗情境（什麼輸入→什麼錯誤結果）
- 沒有具體失敗情境的不算 finding，是風格意見，放最後標「nit」

驗收條件：對象的每個檔案都看過（列出你看過的檔案清單）。

回報格式：finding 條列（嚴重優先）＋看過的檔案清單。無發現就明說「無發現」＋你檢查了哪些面向。
```

## 通用尾註（每個交辦 prompt 最後都貼上）

```
回報合約：只回結論與 檔案:行號；長產物存檔後回傳路徑；
禁止貼整檔內容；失敗時回報嘗試過程與錯誤原文。
你的最終訊息就是回報本體，寫給沒看過你工作過程的人。
```
