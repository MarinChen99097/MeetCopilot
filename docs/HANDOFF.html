1這是什麼（30 秒版）

一個共用核心，餵養三個消費端；對外包裝成兩個產品 surface。

共用核心

CRM ＋ 研究引擎

事先把對方公司、客戶、主管的詳細資料存進 CRM——先用爬蟲填大半欄位、rep 再確認細填。會中還能主動爬對方公司與主管背景。這是整個平台的地基，兩個產品都吃它。

產品 · DynamicSlide

動態簡報

會中依對話內容新增簡報頁當補充說明，一律 append 到簡報尾端。兩種生成路徑：沿用既有風格的 CSS 即時生成、或 AI 生圖。新頁仍需報告者批准才進 deck。

產品 · MeetCopilot

會中副駕

會中即時聆聽對話，把對方公司/主管補充資訊、對手 battlecard、異議處理、下一步建議浮到報告者的 HUD。訊號經批准後回寫 CRM，養厚下一次。

產品 · MeetCopilot

語音模擬訓練

會前用 CRM 裡某位客戶的 persona，讓 AI 用原生語音扮演「那位客戶」與 rep 即時口語對練（可打斷、低延遲），課後產出評分報告。只依賴 CRM、不需會議擷取，可提早開發。

包裝法：傘名沿用 MeetCopilot，平台下含兩個 surface——DynamicSlide（動態簡報）與 MeetCopilot（會中副駕＋語音模擬訓練）。

2會議運作模型

純網頁、不做桌面軟體。實戰時報告者開兩個帳號／兩個瀏覽器 profile。

帳號 A

報告 / presenter（一個 profile）
開 DynamicSlide「播放視圖」
↓
只把「簡報那個分頁」分享進 Meet
↓
播放視圖是乾淨舞台（無 HUD）

帳號 B

接收聲音 / listener（另一個 profile，建議與擷取分頁同 profile）
以靜音＋關鏡頭加入同一個 Meet
↓
Copilot web app 用 getDisplayMedia 擷取「Meet 分頁的音訊」＝所有人混音
↓
送 ASR → 分析 → 研究 → HUD
↓
此瀏覽器永不被分享
報告者用第二裝置（手機／平板）看帳號 B 的 HUD 建議卡・研究卡・逐字稿——只看不擷取，故不限瀏覽器

硬約束

接收端限 Chrome/Edge 桌面——分頁音訊擷取只在 Chromium 桌面（Firefox/Safari/行動不支援） 同 profile ＝可靠路徑——帳號 B 的 Meet 分頁與 Copilot 擷取分頁放同一 profile HUD 檢視端不限——第二裝置只看不擷取，可用手機

三大不變量（架構層強制，從 M1 起生效）

I1只改 pending

deck 變更僅 append 到尾端、不動已播頁；改造引擎只有 APPEND＋pending 尾段 REORDER，移除中段插入。

I2需報告者批准

新頁進 live deck 前必經 approval gate；只有 ACCEPT/EDIT 會 append，未批准客戶永遠看不到。

I3HUD 絕不外流

雙帳號天然隔離（只分享簡報分頁、HUD 在帳號 B／第二裝置）＋播放視圖零 HUD 元素。

研究回填的三個修正

查證後校準

會議 ASR 不用 Live API。Live API 無 speaker diarization、為單一互動使用者設計、單場 ~15 分鐘——不適合被動轉寫會議混音。會議 ASR 改走 Gemini 分段轉寫（藏在 AsrProvider 後），diarization 交下游 LLM；Live API 只用於語音模擬訓練。

查證後校準

AI 生圖一律 pre-meeting。gpt-image-2 有 agentic 規劃階段、實測 medium ~80s 級，會中不可行——生圖坐實為會前預生；會中即時走「沿用風格 CSS 路徑」＋重用已生背景圖，被擋一律 fallback 漸層。

查證後校準

雙帳號建議「同瀏覽器 profile」。分頁 picker 只列同一 Chromium instance 的分頁——可靠路徑＝B 的 Meet 分頁與 Copilot 擷取分頁同 profile。接收端硬限 Chrome/Edge 桌面；列為 S1 spike（最高風險）。

5CRM 資料模型

SQLite / better-sqlite3＋repository 層。欄位刻意很多——爬蟲先填大半、人再細填/驗證。

orgs （租戶根，每張業務表帶 org_id）
users — memberships
賣方側：seller_companies → products → competitors（battlecards）
companies（對方公司，可爬） 可爬英雄表
子表：company_locations · company_news · company_funding_rounds · company_tech
對方產品深檔：company_products → company_product_people；company_departments 決策 18
contacts（主管，可爬 + persona，self-ref reports_to）
deals → deal_contacts（採購委員會）· deal_products
meetings → meeting_attendees · meeting_transcript_segments · meeting_signals
activities（時間軸）· notes（多型自由筆記）
field_provenance 信任層 · embeddings / profile_cards 檢索層 · crawl_jobs

信任層（為何整個 schema 長這樣）

爬蟲便宜能填的（firmographics）恰恰最沒差異化；真正贏單的欄位（persona、優先事項、異議、決策權）恰恰是爬蟲不可信的。所以每個值都帶溯源，流程是：

① 爬蟲填：upsertFromCrawl 在同一 tx 寫實體欄位＋逐欄 field_provenance row（filled_by=crawler＋source_url＋confidence） ② 逐欄 provenance：溯源集中一張表，key＝(entity, field)，值永不與 provenance 漂移 ③ 用戶確認/細填：UI 動作對映到寫入——「確認」設 verified=1；「細填」寫新值＋新 human provenance row ④ 副駕信任規則：優先取 human/verified 值；爬蟲值標信心徽章，confidence<0.6 措辭改「據公開資訊」

模擬訓練逐欄把關：persona 欄位必須逐欄查 provenance（該欄最新未被 supersede 的 row 是 human 或 verified=1 才可用），不看整列 rollup——絕不拿爬蟲猜測幻想。

新的對方產品深檔（決策 18）

撐起副駕「聊到他們某產品時浮出規格/定價/負責人」與研究引擎的對方組織圖。company_products 由爬蟲從官網＋docs＋release notes 先填（產品名、功能、規格、定價頁、整合、公開路線圖）；company_product_people（產品↔人：developer/PM/owner…）與 company_departments（部門/主管/人數，parent 自參照撐組織樹）多為公開資訊拼湊、信心低、需人驗。

6研究引擎

混合式雙引擎——合法自帶引用的 grounding＋深讀指定網址的自建爬蟲。

引擎 A

Gemini Google Search grounding

開放背景研究——公司概況、新聞、主管公開背景。合法、自帶引用、零爬蟲維運。

引擎 B

Playwright 自建爬蟲

搬 ezpagesite「從網址匯入」：stealth 渲染 SPA、子頁連結評分爬取、視覺截圖。quick（單頁、輕量）＝會中即時；detailed（子頁＋截圖）＝會前 CRM 建檔。

SSRF 防護：沿用 v1 SSRF-safe 抽取器，並把檢查掛在對使用者提供 URL 的首次 fetch（ezpagesite 原版缺這個）；擋內網與雲端 metadata（169.254.169.254 等）、外網通。

會中即時研究觸發＝自動＋手動並行：訊號分析偵測新話題/新人名 → 自動發研究（每場設次數/成本上限）；HUD 有「深查」鈕讓報告者點名主題。爬完 → upsertFromCrawl 寫實體欄位＋provenance rows → UI 呈現「確認/細填」。

8風險與誠實揭露

已知風險與待決，攤開講清楚。

  • 混音無乾淨分軌：帳號 B 聽到的是一條混音，失去 presenter/client 分軌 → speaker 靠 LLM 依內容/語氣推斷，準確度未知（S2 驗）。
  • 只 Chromium 桌面（接收端）：Firefox/Safari/行動不支援分頁音訊擷取——硬約束，M0 要向使用者再確認可接受。
  • 同瀏覽器約束：雙帳號需 B 的 Meet 分頁＋Copilot 分頁同 profile，實戰 setup 要教學（可能需一頁操作指南）。
  • 生圖一律會前預生：gpt-image-2 實證慢（medium ~80s 級）、會中不可行；會中誤擋不可在客戶面前發生。前置＝OpenAI 組織驗證＋tier 配額確認。
  • Live API 配額：並發 session 上限依帳號 tier，M4 前查配額頁。
  • 會中研究成本／合規：自動爬對方主管有成本與合規邊界；每場上限＋只蒐集公開資訊＋provenance 溯源；合規責任在使用者（工具僅呈現公開資料）。

9你們現在就能做的三件事

不必等程式碼，這三件現在就能推進、且會直接解鎖最高風險的 spike。

1

實測擷取相容性矩陣

用 Chrome／Edge 打開 tools/capture-test.html（免安裝、雙擊可開），在各裝置×各開會軟體（Meet/Zoom/Teams…）實測分頁音訊擷取，把 PASS/FAIL 填進 tools/README.md 的矩陣。這是 S1 的載具。

2

OpenAI 組織驗證＋查配額

到 OpenAI console 完成 API Organization Verification（未驗證的 org 呼叫 gpt-image-* 會被拒），並查自己帳號的 tier 影像請求配額。這是 S5 生圖的前置。

3

準備兩個 Google 帳號

備妥兩個 Google 帳號、約一場真實 Meet 測試——agent 無法自己開會。這是 S1（最高風險、地基假設）能否成立的必要條件。
