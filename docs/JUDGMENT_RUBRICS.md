# 判斷力外化：Rubrics 與 Checklists

> ⚠️ v2 對齊註記：本檔範例多取材 v1 實戰，rubric 規則仍有效；範例中的操作語彙（INSERT_AFTER／index<=committedIndex 的 INSERT／插入中段）已被 v2 append-only 模型取代（見 00-DECISIONS 決策 13），語彙以 PRODUCT_SPEC v2 為準。模型調度以 MODEL_DISPATCH 使用者拍板覆寫節為準（subagent 一律 opus）。

> 讀者：Sonnet 等級模型。每個 rubric 都是「逐條核對」用的，不是氣氛參考。
> 用法：拿不定主意時，找到對應章節，逐條打勾。勾不滿門檻就照該節的指示行動。
> 每條都附一個正例、一個反例（多數取材自本專案 MeetCopilot 的實際情境）。

---

## R1. 何時升級模型（haiku→sonnet→opus）

先走 `MODEL_DISPATCH.md` 第五節的機械路徑（錯一次/連錯兩次）。以下是機械路徑之外、**該直接跳級**的訊號——任一成立就升：

- [ ] 任務要在**多個彼此衝突的目標間取捨**（例：延遲預算 vs ASR 準確度 vs 成本）
- [ ] 錯了會**很貴或不可逆**（改動會影響 I1/I2/I3、刪資料、對外發佈）
- [ ] 需要**跨 3 個以上組件**的整體理解（例：改 deck model 會同時牽動改造引擎、FSM、HUD）（v2 註：改造引擎已改 append-only——只有 `APPEND`＋pending 區 `REORDER`〔決策 13〕；對應的越權攻擊面是「非 append 的 op／REORDER 觸及 committed 區段」）
- [ ] 前一級模型的輸出「看起來對但你說不出為什麼對」，**且驗證方法本身設計不出來**——升級。（若驗證方法是機械可執行的——重新搜尋、跑測試、read-back——那就直接去驗證，不要升級；本條只適用於判斷型任務）

**正例**：設計「interim transcript 要不要餵進分析層」——牽動延遲、成本、誤報率三方取捨 → 直接指揮官自己想或派 opus，不浪費一輪 haiku。
**反例**：找「committedIndex 在哪個檔案定義」也派 opus——這是 haiku 等級的搜尋，跳級純浪費。

## R2. 何時算「真的完成」（Definition of Done）

宣稱完成前逐條核對，**全部**打勾才能說完成：

- [ ] 驗收條件逐條核對過（交辦時寫的那份，不是事後自己編的寬鬆版）
- [ ] 有 fresh-context agent 的驗證證據（read-back 結果／測試輸出／實跑截圖），不是做事者自己說的
- [ ] **跨模組/前後端的功能：驗過真正的整合路徑**（用真正呼叫方的請求形狀端到端跑），不是只各測一邊（L6）——只測 server 卻沒測前端能不能呼叫到，是漏掉整批契約 bug 的主因
- [ ] 產物已存檔（沒存檔＝沒做）
- [ ] 邊界情況至少想過三個並寫下處理方式（處理了、或明確標「不處理，因為…」）
- [ ] 若改了既有檔：有版本保護（在 git repo → 已 commit 或可 diff 回滾；非 git → 有 `.bak`），且沒有引入與 I1/I2/I3 相悖的行為
- [ ] `WORKLOG.md` 已更新（做了什麼、下一步）

**正例**：「M1 音訊擷取完成」＝有一個能跑的 demo 頁、fresh agent 實跑確認 16kHz PCM frame 有送出、WORKLOG 記錄了「Firefox 不支援 monitorTypeSurfaces，待處理」。
**反例**：「寫好了 capture.js」但沒人跑過、沒驗過 frame 內容——這叫「寫了字」，不叫完成。

## R3. 何時停下來問使用者

**先問再做**（任一成立就停）：

- [ ] 改動會**削弱或繞過 I1/I2/I3**（例：「demo 方便起見先拿掉 approval gate」——停，問）
- [ ] 要**刪除或覆蓋**不是你建立的檔案，且內容與你的預期不符
- [ ] 要花**真金白銀**或建立外部資源（開雲端服務、買 API 額度、發佈、寄出東西）
- [ ] 規格內部矛盾，且兩種解讀會導致**不同的架構**（不是不同的措辭）
- [ ] 需要使用者的**憑證/授權**（MCP OAuth、API key）
- [ ] 任務範圍要**實質擴大**：使用者要 A，你發現不做 B 就沒法做 A，且 B 符合任一——需要自己的一套驗收條件／要新增或修改的檔案數 ≥ A／預估交辦輪數 ≥ A。符合就問，不要自行心證「工作量比例」

**不要問、自己決定**（問了反而浪費使用者時間）：

- 有慣例預設值的技術選擇（命名、目錄結構、測試框架）→ 選主流的，記在 WORKLOG
- 可逆且便宜的嘗試 → 做了再報告。**但凡觸及 I1/I2/I3 者不適用本條豁免**——即使可逆也回上方「先問再做」清單（上方清單永遠優先於本清單）
- 規格已寫明的事 → 讀 `PRODUCT_SPEC.md`，不要拿規格裡有答案的問題去問

**正例**：發現「Google Meet 分享分頁時，分頁音訊擷取與被分享分頁是同一個，會把自己簡報的聲音也錄進去」——這是規格級矛盾，整理清楚後問。
**反例**：問「slide spec 的 JSON 欄位要叫 title 還是 heading」——自己定，記下來就好。

## R4. 方向錯誤的訊號（換路，不是重試）

重試＝同方法再來一次；換路＝改變方法或回頭質疑前提。出現以下任一訊號，**禁止**原地重試：

- [ ] 同一件事已失敗**兩輪**（`MODEL_DISPATCH.md` 硬限制）
- [ ] 每次修好 A 就弄壞 B，修好 B 又弄壞 A（打地鼠模式＝架構層有錯）
- [ ] 為了讓方案成立，需要的「特例/補丁」數量隨進展**變多而不是變少**
- [ ] 你開始想「把驗收條件改寬一點就過了」——這是方向錯的最強訊號
- [ ] 方案依賴一個**沒驗證過的假設**（例：「瀏覽器應該可以擷取耳機輸出」——先做 5 分鐘的 spike 驗證假設，再繼續蓋）

換路的動作：停 → 用一段話寫下「原本的路、失敗證據、懷疑的前提」→ 產生 2–3 個替代路線 → 按 R1 判斷該誰來選（多半值得升級或問使用者）。

**正例**：試了兩輪都無法在純 Web 擷取系統音訊 → 不再試第三種 hack，改列「Electron loopback vs 要求客戶用分頁分享」兩條路線給使用者選。
**反例**：同一個 WebSocket 重連 bug，換五種措辭叫同一個 sonnet agent 修五次。

## R5. 品質底線怎麼驗（最低可接受標準）

不同產物的底線與驗法。低於底線不准交付：

| 產物 | 底線 | 驗法 |
|---|---|---|
| 程式碼 | 能跑＋核心路徑有測試或實跑證據＋不違反 I1/I2/I3 | fresh agent 跑測試/實跑；涉及 deck 操作時，用「試圖改 `index <= committedIndex` 的頁」當攻擊測試，必須被 reject（v2：對應攻擊面＝「非 append 的 op／REORDER 觸及 committed 區段」，須被 reject；決策 13） |
| 授權/隔離不變量 | 用「不該有權的身分」測會被拒 | **用攻擊者的憑證去打**（另一 user／另一 org／非 presenter 角色的真實 token），確認被拒——不是用本人 happy-path token 測（那對授權漏洞是盲的，L7） |
| 文件 | 弱模型讀完能照做（有具體步驟/門檻/範例），無死連結 | 派 haiku agent 讀，要求它複述「照這份文件，X 情況我該做什麼」，答錯＝文件不合格 |
| 研究/比較報告 | 每個結論有來源；有「不確定」區；有明確建議而非羅列 | 抽 2 個關鍵事實交叉驗證來源 |
| 交辦 prompt | 含三要素（目標動機/驗收/回報格式） | 對照 `TASK_TEMPLATES.md` 模板逐欄檢查 |
| 對外/不可逆動作 | 使用者明確同意 | 找得到同意的原話，找不到＝沒同意 |

**正例**：guard 函式寫完後，驗證 agent 用 `applyPatch({index: committedIndex})` 攻擊，確認回 reject——這才算驗過 I1。
**反例**：「程式碼看起來邏輯正確」＝零證據，不算驗證。

## R6. 模糊題與品味判斷（誠實條款）

拆解、驗證、多樣本評審補得了**執行品質**；補不了**模糊題與品味**（UI 好不好看、文案語氣、商業取捨）。遇到時不要硬裝有判斷力，照下面做：

1. 能升級就升級模型（opus），並明說「這是品味判斷，我的信心低」。
2. 產 2–3 個方案附各自 trade-off，讓使用者選——**不要自己拍板然後藏起不確定性**。
3. 都不行就直說做不到，標註在交付物裡。

**實例（L10）**：會中生成新頁的「插入位置與風格參考」怎麼選，是設計判斷。程式寫得再正確、typecheck／冒煙／對抗審查全過，設計選錯了照樣是錯的——這種錯只有使用者會發現。所以：能自動驗證的執行品質才交給 subagent＋審查；「怎麼做才對」的設計/品味取捨，早點攤方案給使用者選。（v2 註：插入位置已改為一律 append 到尾端〔決策 13〕；此處保留為「設計取捨要攤給使用者選」的實例，插入位置的具體行為以 v2 為準。）

## R7. 遇到令人警覺的訊號：先讀「地面真相」，別對 pattern 動手（L9）

出現「像是某個已知災難」的訊號時（檔案好像被截斷、依賴好像沒裝、測試好像全掛），**先核對地面真相再動手改狀態**：

- [ ] 用權威來源看實際內容/根因：檔案疑似毀損 → 用 Read 讀實際內容（不是信某個行數/大小指標）；命令疑似失敗 → 讀實際錯誤訊息與根因，不是憑錯誤「長得像」就下結論
- [ ] 確認成因**真的**是你以為的那個，才執行對應的修復（尤其是重裝、reset、刪檔、覆寫這類會改狀態的動作）
- [ ] pattern-match 到熟悉的失敗 ≠ 成因相同

**正例**：PowerShell 行數顯示制度檔剩 6 行、像被截斷 → 先 Read 看實際內容，發現檔案完好（是 `Measure-Object -Line` 對 LF 行尾數錯），沒有誤刪重建。
**反例**：`app-builder.exe` spawn ENOENT 像安裝壞了 → 反覆 npm install/降版/清 lock 四次（真因是防毒隔離該 exe，重裝永遠沒用，見 L8）。

## R8. 審查迴圈與 Plan Gate 判定（改編自 ezpage engineering-sop）

補 R2（何時算完成）與 R5（品質底線）的**流程**：R2/R5 是門檻，本節是「怎麼跑到門檻」與「使用者回應怎麼算核准」。

### 嚴格審查迴圈（改完 code 後，Mandatory）

完整審查鏈（依序）：

1. **scenario-verification skill**（`.claude/skills/scenario-verification/`）→ 驗「對不對」：代入真實值追資料流、可達性、邊界、Write-Reader 交叉驗證。
2. **`/simplify`**（harness 內建）→ 驗「好不好」：重用性、可讀性、效率、有無多餘程式碼。
3. **code-review skill**（`.claude/skills/code-review/`）→ 驗「安不安全＋合規」：金鑰洩漏、I1/I2/I3、SSRF/authz、契約一致。
4. 條件式追加：改動涉及 auth / input validation / file upload / 外部 I/O → 加做安全專項審查。

**迴圈規則（照做）：**
- [ ] 發現問題（含**非本次改動造成**的）→ 自行修正 → 修正後**從 #1 重跑完整審查鏈**（不是只重跑出問題那一支）。
- [ ] 重複此迴圈，**直到最後一輪審查零問題**（全 PASS，無任何需修正項目）才算通過。
- [ ] **不可因「只改了一小處」就跳過重審**——任何修改都可能引入新問題。
- [ ] 審查由 fresh-context agent（一律 opus，見 MODEL_DISPATCH 覆寫節）執行，不是做事者自評（呼應 R2）。

**正例**：改 deck guard 後 code-review 抓到一個越權面 → 修 → **重跑 scenario-verification＋simplify＋code-review 整條** → 這輪全 PASS 才宣告完成。
**反例**：code-review 抓到一個問題，只改那一處、只重跑 code-review 一支就交付——漏了新改動可能破壞的資料流（該重跑 #1）。

### Plan Gate 核准判定（複雜任務 plan 呈給使用者後）

| 使用者回應 | 判定 | 動作 |
|-----------|------|------|
| 不含修改建議的肯定（"go" / "ok" / "好" / "approve" / "繼續" / "可以" / "沒問題"） | **核准** | 進入執行階段 |
| 含具體修改建議（「把 X 改成 Y」「不要用 Z」） | **需修正** | 修正 plan → 重新呈現 → 等下一次核准 |
| 提問（「為什麼選 X？」「Y 是什麼？」） | **需解釋** | 回答問題，**不改 plan**（除非答案改變方案） |

**正例**：使用者回「這個方向可以，但 approval gate 別放前端」→ 判定「需修正」→ 改 plan 重呈，不當作核准就開工。
**反例**：使用者問「為什麼選 append-only？」就當成核准直接動工——那是提問不是核准。
